# ADR-006 — The sandbox is a hard security boundary from Stage 1

- **Status:** Accepted
- **Date:** 2026-09-01

## Context

The platform executes code it did not write: existing repository test suites,
and patches generated by an LLM. Repository content is untrusted input, and an
LLM's output is not trustworthy by construction. A malicious repository can also
attempt prompt injection to influence what the agent chooses to run.

Executing any of that in the API process would expose the database, the host
filesystem, and every credential in the process environment.

## Decision

All repository code and all AI-generated code executes only inside a Docker
container that is created per run and destroyed afterwards, with:

- a CPU limit;
- a memory limit;
- a hard wall-clock timeout;
- **no network access** (`--network none`);
- a non-root user;
- a read-only root filesystem, with a single writable workspace mount;
- captured stdout, stderr, and exit code;
- guaranteed teardown, including on timeout and on error.

This holds from Stage 1. It is not deferred as a "production hardening" task.

## Alternatives considered

- **Run tests in the worker process.** Simplest and fastest. Rejected outright:
  it gives arbitrary repository code the worker's database credentials.
- **`chroot`/subprocess isolation.** Weaker; does not constrain CPU, memory, or
  network.
- **gVisor / Firecracker / Kata.** Stronger isolation than Docker, and the right
  answer for genuinely hostile multi-tenant input. Deferred: they add real
  operational cost, and Docker with these constraints is a reasonable Stage 1
  boundary for repositories the user has chosen to connect.

## Consequences

**Positive**

- One explicit, testable boundary. Its properties can be asserted in tests:
  timeout kills the run, the network is unreachable, containers are removed.
- Resource limits stop a runaway test suite from taking down the host.

**Negative**

- Container startup adds latency to every test run.
- No network means dependency installation must be handled by pre-built images
  or a pre-populated cache, which constrains which repositories can be tested.
- Docker socket access is itself sensitive and must be tightly scoped.

**Non-negotiable:** no feature may execute untrusted code outside this boundary
for convenience, including during development.
